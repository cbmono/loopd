# loopd 3.4.0

**The first mods, and a usage line that says where a round's cost went.** Claude Code 2.1.287
made plugins able to run code inside the session (mods). Two ship here as companion plugins,
installed only if you choose to: one records a session's usage in the plugin store as it
happens, one draws the board as a pane inside the project-manager's session. Neither
changes a gate; both are deletable; core runs exactly as before without them.

**6 merged pull requests since 3.3.2.**

## The usage line names the tools and the failures (#355)

`usage tokens=N tools=N ms=N cached=N errors=N by=Bash:152,Agent:30,Edit:13` — the top five
tools by call count and the number of failed calls, read from the session transcript. Step 4
writes one `thrashing:` note when failures exceed 20% of calls on a round of at least 20;
report-only, never a re-dispatch. Measured baseline on a healthy tick: 7 failures in 236.

## `loopd-mod-usage` (#357, #359)

A mod that records `input`, `output`, `cacheRead`, `cacheWrite`, requests, turns, wall time,
model, tool counts by name and tool errors under `loopd.usage.<session id>` in the plugin
store after every turn. `session-usage.sh` reads the store first and the transcript second,
`usage UNKNOWN` on any doubt as before. Measured on 2.1.293: a mod loaded in a `claude -p`
or a detached `claude --bg` session fires `turn.step` and `turn.complete` with usage; a
`--bg` session fires no `session.end` after its turn, so the record is complete at every
`turn.complete` (`docs/spikes/mods-in-background-sessions.md`).

## `loopd-mod-pane` (#358)

`/board` opens a pane that renders `SNAPSHOT.json` — the fourth renderer over the board's
one contract, re-deriving nothing from the bundle and drawing nothing outside the field
allowlist. Two buttons: **Tick** runs `/loopd:dispatch` in this session once it is idle
(`$.command.run`; the host refuses a `/`-prefixed `$.prompt.submit`), **Refresh** re-reads.
Off by presence like the rest of the board: no snapshot, one line saying so.

## What a mod may do here (#357)

`tests/mods.test.sh` holds every `plugin-mod-*/` to the same rule: no model call, no
permission decision (`tool.check`), no process, no network, no environment; file reads only
for paths the README declares; never a file write. The gate's `claude` shim now lets exactly
`claude plugin test` and `claude plugin validate` through to the real binary (no session,
no network, no spend) and refuses everything else as before; both skip by name where no
CLI exists, so CI does not run them — run them locally before merging a mod.

## Not built, and why

A spawn-policy mod (`agent.spawn`: refuse Haiku, apply `roleTiers`) was planned and
dropped: that event fires for subagents and teammates, not for the `claude --bg` processes
loopd launches from Bash, so it would never reach a role agent. The completion-signal mod
is open as its own change and follows in the next release.

## The release question

*For each hook, gate and script, which assumption has this model generation made
unnecessary?* One: that the only way to read a session's cost is to parse its transcript
afterwards. A mod reads it as it happens. The transcript parser stays as the fallback and
is still what a bundle without the companion uses.
